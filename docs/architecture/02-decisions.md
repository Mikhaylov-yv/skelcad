## D1. Мультиязычность модели — принято (2026-10-19)

**Решение**: исполняемая часть (генераторы, правила, расчёты) — только Python, исполняется на сервере
в изолированном воркере (D13). Протокол для плагинов на других языках не описываем, пока не появился
первый такой плагин. Данные модели — JSON Schema (смысл 2), тексты — поле `Text` со словарём языков
(смысл 1); сообщения правил остаются русскими до workbench (M2).

Исходная постановка вопроса (сохранена для истории):

В редакции 0.1 вопрос был поставлен узко («YAML + Python или только Python»). Правильная
постановка: модель должна быть мультиязычной в трёх смыслах сразу.

**1. Человеческие языки.** Все тексты модели (наименования деталей, заметки, допущения,
сообщения правил, пункты норм) — многоязычные поля: `name: {ru: "Плита опорная", en: "Base plate"}`
с языком по умолчанию на уровне проекта. Замечания правил генерируются из шаблонов пакета
стандарта на языке пользователя. Агент пишет на том языке, на котором говорит конструктор.

**2. Нейтральность данных.** Сама модель — не Python-объекты, а данные по открытой JSON Schema
(хранятся как YAML/JSON). Её читает и пишет любой язык программирования и любой агент без
нашего кода. Это уже заложено в принципе 1 и не обсуждается.

**3. Языки программирования для исполняемой части** (генераторы топологий, правила, расчёты).
Здесь три варианта:

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| (а) Только Python в песочнице | как в пилоте: генератор = Python-модуль с build123d | быстро; агенты лучше всего знают CadQuery/build123d; одна среда исполнения | участники из мира C#/.NET (SolidWorks, КОМПАС) и TypeScript не могут писать плагины; песочница Python слабая |
| (б) Плагины как внешние процессы по протоколу (JSON-RPC через stdio, как LSP и MCP) | ядро говорит с генератором/правилом через схему «вход: модель → выход: геометрия/замечания»; эталонная реализация на Python, но плагин может быть на C#, Rust, TS | язык любой; естественная изоляция процессом (таймаут, память, права); адаптеры САПР на C# ложатся в ту же схему | геометрия через границу процесса — только как STEP/BREP-файл или тесселяция, медленнее; сложнее отладка |
| (в) WASM-плагины | генераторы компилируются в WebAssembly и исполняются в ядре | лучшая песочница и переносимость | OCCT в WASM тяжёлый и незрелый; агентам непривычно; преждевременно |

**Рекомендация**: (а) + (б) одновременно. Внутри ядра — Python-плагины первого класса
(скорость, агенты); снаружи — тот же контракт как JSON-RPC-протокол, чтобы правило или
генератор можно было написать на любом языке. Протокол плагина описывается в той же
JSON Schema, что и модель. (в) — не раньше, чем OCCT-в-WASM станет промышленным.

Открытый вопрос к вам: достаточно ли смыслов 1–3, или под «мультиязычной» имелось в виду
ещё что-то (например, несколько языков описания геометрии: build123d, CadQuery, KCL, OpenSCAD
как взаимозаменяемые генераторы)? Это тоже укладывается в (б): генератор на KCL — просто
плагин-процесс с движком Zoo.

## D2. Рабочее место конструктора — принято (2026-10-12)

**Решение**: web-приложение в браузере, одинаковое для всех форм развёртывания; ядро работает
как сервер. Порядок форм: self-hosted образ первым, публичная площадка как наш экземпляр того же
образа, настольная оболочка (Tauri + sidecar) позже и только по спросу. Главный критерий —
простота для обычного инженера: ему ничего не нужно ставить, кроме моста к САПР для режима Б.

**За и против публичной площадки, которые взвешивали** (сохранено для истории):
за — нулевой порог входа, одна версия, сетевой эффект («GitHub для конструкций»), тяжёлые
расчёты на сервере, стандартный удалённый MCP (Streamable HTTP + OAuth 2.1), совпадение с
практикой ExcaliDash/drawio.br; против — конфиденциальность КД (главный барьер для
предприятий), исполнение чужого кода на общем сервере, режим Б всё равно требует локального
моста, стоимость и ответственность сервиса, задержки/офлайн, недоверие к «open source только
в нашем облаке», зависимость от LLM-провайдеров при хостинге агентов. Self-hosted-первым
снимает первый, четвёртый и шестой пункты, остальные закрываются песочницей и мостом.

с 3D-diff и кнопками принять/отклонить, сравнение вариантов, правка параметров, замечания
агенту, установка без Python, Windows прежде всего.

В4 — тонкая панель моста в режиме Б; В3 и В5 не делаем.

## D4. Лицензия — принято

Apache-2.0 для ядра, агентного API, рабочего места и адаптеров. Совместимо с build123d,
OCCT (LGPL + exception), agentcad. Код под AGPL (например, SolidPilot) не заимствуем.
Пакеты стандартов могут иметь свою лицензию (открытый каркас — Apache-2.0, слой данных —
по источнику).

## D11. Сервер с встроенной точкой MCP — принято (2026-10-19)

SkelCAD — сервер (FastAPI), MCP — одна из его точек: `https://skelcad.br/mcp` (Streamable HTTP,
SDK `mcp` 1.x), вход по Bearer-токену клиента; имя клиента становится автором коммитов. Локальный
запуск по stdio не делаем. Пользователи и OIDC — M2. Подробно: `04-m1-plan.md`.

## D12. Изменения агента — обычные коммиты в git — принято (2026-10-19)

Проект на сервере — git-репозиторий; каждый пишущий инструмент — коммит под именем агента
с сообщением «что и зачем». Папок предложений и веток нет; конструктор смотрит историю и
откатывает (`revert`). Согласование как сущность (лента с кнопками) — M2 вместе с workbench.
Целевая аудитория — обычные конструкторы, которые могут не знать git: проекты живут на сервере,
синхронизация с внешним origin — необязательная.

## D13. Сборки в изолированном воркере с лимитами — принято (2026-10-19)

Код проекта исполняется только в контейнере-воркере (без сети, лимиты CPU/памяти/процессов),
каждая задача — подпроцесс с таймаутом и audit-hook (запись только в `out/`, без процессов и
сети). Контейнер на задачу с усиленной изоляцией — M2 (публичная площадка).

## D14–D17. Рабочее место (M2) — принято (2026-10-19)

- **D14. Фронтенд.** Отдельное приложение `web/` (Vite + TypeScript + React; three.js через
  `@react-three/fiber`/`drei` для 3D, SVG в React для эскизов и видов), статика отдаётся сервером
  по `/`, браузер ходит в `/api` поверх тех же `tools.py`. Отвергнуты htmx и `three-cad-viewer`.
- **D15. Вход.** Keycloak realm `home` через oauth2-proxy (как drawio.br); сервер берёт
  пользователя из заголовков прокси в режиме `SKELCAD_AUTH=proxy`; коммиты из workbench — от имени
  пользователя; `/mcp` остаётся на токенах; `/out` уходит за вход. Одна команда, группа `admins`.
- **D16. Задача агенту из workbench, любой провайдер LLM.** Контейнер `agent` ведёт цикл с моделью
  по OpenAI-совместимому API (OpenRouter, LiteLLM, Ollama, vLLM, …; `SKELCAD_LLM_*`), инструменты —
  те же MCP-инструменты сервера через MCP-клиент; запасной исполнитель — headless Claude Code.
  Привязки к одному провайдеру нет (требование пользователя). Ход задачи виден в ленте, на время
  задачи проект «у агента» (D6). Учётные данные — одна сервисная запись сервера.
- **D17. Черновик параметров.** Правка в форме собирается во временном снимке и показывается
  как разница с HEAD; коммит — только по «Сохранить».

Принципы интерфейса: ISO 9241-110 (пригодность задаче, самоописательность, управляемость,
устойчивость к ошибкам) и эвристики Нильсена как чеклист ревью каждого шага. Подробно:
`05-m2-plan.md`.

## D18–D21. Компоновка, эскизы с размерами и сравнение (M2.1) — принято (2026-10-19)

- **D21. Компоновочный эскиз — по скелету и обстановке, до геометрии.** Из одного `project.yaml`:
  базы, интерфейсы с параметрами, зоны keep_in/keep_out, нагрузки стрелками, ограничения; обстановка —
  новый раздел `skeleton.surroundings` (стена, пол, труба, ответная деталь, соседнее оборудование как
  простые тела с ролью и именем). Согласование — пометки конструктора на эскизе и кнопка «Компоновка
  согласована» (коммит, `status: approved` у сущностей скелета; изменения после — предупреждение).
  Набросок конструктора (фото, скан) прикладывается к задаче, агент переводит его в скелет.

- **D18. Эскиз = проекция по геометрии + размеры по модели.** Линии — HLR-проекция OCCT (как сейчас),
  размеры строятся из модели и привязаны к сущностям (деталь, отверстие, крепёж, труба); правила
  расстановки автоматические, сверх них — раздел `sketch` варианта (явные размеры, скрытие лишних).
  Отвергнуты: свой интерактивный редактор размеров в браузере; размеры из САПР через адаптер (M3/M5).
- **D19. Сравнение — в одном масштабе и наложением.** Экран «Сравнение»: эскизы вариантов рядом в
  общем масштабе, наложение двух вариантов (синий — базовый, красный — сравниваемый), в таблице —
  различающиеся размеры и параметры вариантов.
- **D20. Эскиз — не чертёж.** Без рамки, основной надписи, допусков, шероховатости, DXF/DWG (это M5);
  эскиз идёт в «Выдачу» (SVG, PNG) и агенту через `render`.

Подробно: `06-m2-1-sketches-plan.md`. Приняты конструктором 2026-10-19; раздел обстановки в модели назван `skeleton.surroundings`, согласование — блок `layout` в `project.yaml` с хешем (см. план, уточнения шага 1).

## D22–D27. Масштабирование: ввод компоновки, PMI, дерево узлов, граф связей — принято (2026-10-20)

Обсуждение 2026-10-20 (универсальность от планки до большого насоса, вход от руки, PMI как в NX, дерево
компоновок, база данных); материал — `docs/research/research_notes/Мировая практика — компоновка, PMI, дерево узлов, база связей.md`.
Опора: Pahl & Beitz и VDI 2221 (preliminary → definitive layout, модульная структура), ASME Y14.24 (design
approval layout), ASME Y14.41 / ISO 16792 / ГОСТ Р 2.052-2024 (MBD, сохранённые виды), Creo skeleton и NX WAVE
(публикация интерфейсов и space claims), NASA SE Handbook (распределение, запасы, ICD), DSM, Speckle и SysML v2
API (версии поверх графа объектов).

- **D22. Компоновка редактируется через виды, YAML остаётся единственным источником.** Вход конструктора —
  три канала в один `project.yaml`: набросок от руки (фото, планшет) к задаче агента и в репозиторий как
  исходный документ, агент переводит его в скелет и обстановку; правка существующей компоновки прямо на
  эскизе (сдвинуть короб, растянуть зону, ввести число по размеру — каждое действие коммит конструктора);
  доска со свободными штрихами как пояснение. Солвер ограничений для компоновки не нужен: сущности заданы
  числами. Отвергнуто: графический редактор как отдельный источник истины.
- **D23. PMI — семантические сущности модели с видами.** Допуски на размеры и посадки (ISO 286), общие допуски
  (ГОСТ 30893) правилом по умолчанию, шероховатость на грань, минимальный набор допусков формы и расположения,
  технические требования, обозначения швов — привязаны к отверстиям, кромкам и граням по роли, а не к номерам
  граней ядра. Вид — объект: направление, область, сечение, набор PMI; один вид даёт лист 2D и подписи в 3D
  в плоскости аннотаций (как виды модели NX и saved views ASME Y14.41). Правила проверяют PMI; выход в САПР —
  STEP AP242 с семантическим PMI.
- **D24. Узел дерева — проект; распределение вниз, сводка вверх.** Составной узел делит себя на дочерние и
  выделяет каждому зону `keep_in`, интерфейсы с нагрузками и потоками, бюджеты массы и стоимости с запасом.
  Обстановка ребёнка выводится из родителя (зоны и фактические габариты соседей, тела родителя), не пишется
  руками. Вверх поднимается сводка (оболочка, масса и ЦТ, положения интерфейсов, реакции); родитель проверяет
  её теми же проверками (вписался, не задевает соседей, бюджеты). Хеш согласования ребёнка включает исходные
  данные от родителя. Хранение — один git-репозиторий, узлы папками; вариант родителя выбирает варианты детей;
  система координат ребёнка задаётся базой родителя (сначала повороты на прямой угол); сборка родителя берёт
  готовую геометрию детей из кэша по хешу. Контекст агента на узле: сам узел, исходные данные от родителя, по
  строке на соседа и на ребёнка; глубже — явным вызовом; параллельные агенты по соседним узлам.
- **D25. Запросы на изменение к родителю.** Исходные данные от родителя для ребёнка только для чтения;
  нарушение даёт замечание с величиной запаса на границе; ребёнок перепроектирует или отправляет запрос на
  изменение в ленту родительского узла; родитель переназначает зону или бюджет, согласование пересматривается
  по цепочке (практика ECR/ECO, ISO 10007). Покупные компоненты — узлы особого вида: зона и интерфейсы из
  каталога как пакет, проработка — выбор.
- **D26. Excalidraw — эксперимент для доски** (MIT, React-компонент, у конструктора уже есть excalidash);
  tldraw отвергнут (водяной знак или платная лицензия); JSketcher, Chili3D, planegcs — позже для профилей
  деталей, не для компоновки.
- **D27. База данных: git с YAML остаётся системой записи, граф связей — производный индекс в Postgres.**
  Сущности и связи всех проектов извлекаются из `project.yaml` и комплекта сборки при каждом коммите и сборке;
  словарь типов связей задан явно, адресация глобальная (`проект`, `вариант`, `kind:id[/kind:id]`); индекс
  одноразовый (удалить и пересобрать из git). Запросы — рекурсивный SQL; Apache AGE или Neo4j — только для
  анализа. Операционные данные (задачи, лента, очередь) переезжают в ту же базу при втором экземпляре сервера;
  замечания и согласование остаются в git. Postgres сразу, без SQLite (конструктор, 2026-10-20); локально и в
  тестах — встроенный сервер `pgserver`. Граница пересмотра системы записи: узел больше мегабайта,
  одновременная правка одного узла в реальном времени, транзакции через несколько репозиториев, миллионы
  сущностей — тогда TerminusDB или Dolt (сохраняют ветки и diff) либо хранилище объектов по хешу по образцу
  Speckle; собственные микроверсии по образцу Onshape не рассматривать. Словарь API — по образцу SysML v2
  (проект, коммит, ветка, элемент, связь), структура — ГОСТ 2.053.

Подробно: `07-m2-2-graph-plan.md` (M2.2) и дорожная карта в нём (M2.3 ввод компоновки, M2.4 PMI и виды,
M3 дерево компоновок, M4 мост к САПР).

## D28. Вложения конструктора — в репозитории проекта, агент получает их как изображение — принято (2026-10-21)

Набросок, фото, экспорт из доски прикладываются к задаче агенту и хранятся в папке `attachments/` репозитория
проекта коммитом конструктора (загрузка до 16 МБ; png / jpg / webp / svg / pdf / excalidraw; растр уменьшается
до 3000 px по длинной стороне — набросок, не архивный документ). Агент получает вложение инструментом
`attachment(project, path)` как изображение MCP; встроенный агент передаёт его модели как `image_url` в первом
сообщении, а картинки из инструментов — пользовательским сообщением после ответов инструментов. Росчерки
пометок — в `review.yaml` (точки в координатах модели и вид), видны на эскизе и в PNG у агента. Отвергнуто:
отдельное хранилище файлов вне git (теряется история и привязка к коммиту); ссылки на внешние диски.
Уточнение D26 (2026-10-21): доска — инструмент рисования наброска, вход через вложения; выгрузка компоновки в
доску отложена до результата правки на эскизе. Подробно: `08-m2-3-layout-input-plan.md`.

## D6–D10 — отложено, материал для размышления

- **D6. Совместная работа.** Строгая очерёдность на уровне набора изменений (ветка агента в git,
  конструктор принимает merge) против одновременной правки. Обзор: ни одного подтверждения
  в пользу одновременной правки с агентом, Onshape сам рекомендует ветки. Склоняюсь к очерёдности.
- **D7. Адаптер SolidWorks.** Python/COM с early binding сейчас; .NET-добавление после
  стабилизации протокола рецепта. Если ядро примет D1(б), адаптер на C# — обычный плагин-процесс.
- **D8. Дистрибуция — принято вместе с D2.** Self-hosted образ (`docker compose`) первым;
  публичная площадка как экземпляр; у инженера только подписанный мост к САПР; настольная
  сборка Tauri + sidecar + MSIX/winget — позже по спросу.
- **D9. Режим выдачи.** Для SolidWorks/КОМПАС основной — Б (STEP не несёт дерева); режим А
  (готовый комплект) — для малых КБ и стран без лицензий САПР; состав комплекта А определить
  после пилота M2.
- **D10. Пакет стандарта.** Двухслойный: открытый каркас (схема, правила-плагины, шаблоны,
  i18n) + слой данных (таблицы) с указанием источника или поставляемый пользователем.
  Прототипы формата: `package.xml` FreeCAD, реестр `standards[]` BOLTS, правила в духе IDS /
  `.swstd`, SVG-шаблоны TechDraw с autofill. Юридическая проверка до публикации `std-gost`.
