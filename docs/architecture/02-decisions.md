## D1. Мультиязычность модели — принято (2026-10-19)

**Решение**: исполняемая часть (генераторы, правила, расчёты) — только Python, исполняется на сервере
в изолированном воркере (D13). Протокол для плагинов на других языках не описываем, пока не появился
первый такой плагин. Данные модели — JSON Schema (смысл 2), тексты — поле `Text` со словарём языков
(смысл 1); сообщения правил остаются русскими до workbench (M2).

Исходная постановка вопроса (сохранена для истории):

В редакции 0.1 вопрос был поставлен узко («YAML + Python или только Python»). Правильная
постановка: модель должна быть мультиязычной в трёх смыслах сразу.

**1. Человеческие языки.** Все тексты модели (наименования деталей, заметки, допущения,
сообщения правил, пункты норм) — многоязычные поля: `name: {ru: "Плита опорная", en: "Base plate"}`
с языком по умолчанию на уровне проекта. Замечания правил генерируются из шаблонов пакета
стандарта на языке пользователя. Агент пишет на том языке, на котором говорит конструктор.

**2. Нейтральность данных.** Сама модель — не Python-объекты, а данные по открытой JSON Schema
(хранятся как YAML/JSON). Её читает и пишет любой язык программирования и любой агент без
нашего кода. Это уже заложено в принципе 1 и не обсуждается.

**3. Языки программирования для исполняемой части** (генераторы топологий, правила, расчёты).
Здесь три варианта:

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| (а) Только Python в песочнице | как в пилоте: генератор = Python-модуль с build123d | быстро; агенты лучше всего знают CadQuery/build123d; одна среда исполнения | участники из мира C#/.NET (SolidWorks, КОМПАС) и TypeScript не могут писать плагины; песочница Python слабая |
| (б) Плагины как внешние процессы по протоколу (JSON-RPC через stdio, как LSP и MCP) | ядро говорит с генератором/правилом через схему «вход: модель → выход: геометрия/замечания»; эталонная реализация на Python, но плагин может быть на C#, Rust, TS | язык любой; естественная изоляция процессом (таймаут, память, права); адаптеры САПР на C# ложатся в ту же схему | геометрия через границу процесса — только как STEP/BREP-файл или тесселяция, медленнее; сложнее отладка |
| (в) WASM-плагины | генераторы компилируются в WebAssembly и исполняются в ядре | лучшая песочница и переносимость | OCCT в WASM тяжёлый и незрелый; агентам непривычно; преждевременно |

**Рекомендация**: (а) + (б) одновременно. Внутри ядра — Python-плагины первого класса
(скорость, агенты); снаружи — тот же контракт как JSON-RPC-протокол, чтобы правило или
генератор можно было написать на любом языке. Протокол плагина описывается в той же
JSON Schema, что и модель. (в) — не раньше, чем OCCT-в-WASM станет промышленным.

Открытый вопрос к вам: достаточно ли смыслов 1–3, или под «мультиязычной» имелось в виду
ещё что-то (например, несколько языков описания геометрии: build123d, CadQuery, KCL, OpenSCAD
как взаимозаменяемые генераторы)? Это тоже укладывается в (б): генератор на KCL — просто
плагин-процесс с движком Zoo.

## D2. Рабочее место конструктора — принято (2026-10-12)

**Решение**: web-приложение в браузере, одинаковое для всех форм развёртывания; ядро работает
как сервер. Порядок форм: self-hosted образ первым, публичная площадка как наш экземпляр того же
образа, настольная оболочка (Tauri + sidecar) позже и только по спросу. Главный критерий —
простота для обычного инженера: ему ничего не нужно ставить, кроме моста к САПР для режима Б.

**За и против публичной площадки, которые взвешивали** (сохранено для истории):
за — нулевой порог входа, одна версия, сетевой эффект («GitHub для конструкций»), тяжёлые
расчёты на сервере, стандартный удалённый MCP (Streamable HTTP + OAuth 2.1), совпадение с
практикой ExcaliDash/drawio.br; против — конфиденциальность КД (главный барьер для
предприятий), исполнение чужого кода на общем сервере, режим Б всё равно требует локального
моста, стоимость и ответственность сервиса, задержки/офлайн, недоверие к «open source только
в нашем облаке», зависимость от LLM-провайдеров при хостинге агентов. Self-hosted-первым
снимает первый, четвёртый и шестой пункты, остальные закрываются песочницей и мостом.

Требования из документа: привычный визуал (3D, дерево, разрезы, измерения), лента предложений
с 3D-diff и кнопками принять/отклонить, сравнение вариантов, правка параметров, замечания
агенту, установка без Python, Windows прежде всего.

| | В1. Браузер + локальный сервер | В2. Настольное приложение (Tauri + Python-sidecar) | В3. Расширение VS Code | В4. Панель внутри САПР (SolidWorks Taskpane / FreeCAD Workbench / КОМПАС-библиотека) | В5. Electron |
|---|---|---|---|---|---|
| Что видит конструктор | вкладка браузера `localhost` | отдельное окно, иконка, инсталлятор | VS Code с 3D-панелью (как ocp-vscode) | своя панель в родной САПР, 3D — в самой САПР | отдельное окно |
| Установка для инженера | инсталлятор ядра + любой браузер | один MSIX/winget, прецедент GeoLibre | VS Code + расширение + ядро | добавление/плагин САПР + ядро | один инсталлятор, +150 МБ Chromium |

В4 — тонкая панель моста в режиме Б; В3 и В5 не делаем.

## D4. Лицензия — принято

Apache-2.0 для ядра, агентного API, рабочего места и адаптеров. Совместимо с build123d,
OCCT (LGPL + exception), agentcad. Код под AGPL (например, SolidPilot) не заимствуем.
Пакеты стандартов могут иметь свою лицензию (открытый каркас — Apache-2.0, слой данных —
по источнику).

## D11. Сервер с встроенной точкой MCP — принято (2026-10-19)

SkelCAD — сервер (FastAPI), MCP — одна из его точек: `https://skelcad.br/mcp` (Streamable HTTP,
SDK `mcp` 1.x), вход по Bearer-токену клиента; имя клиента становится автором коммитов. Локальный
запуск по stdio не делаем. Пользователи и OIDC — M2. Подробно: `04-m1-plan.md`.

## D12. Изменения агента — обычные коммиты в git — принято (2026-10-19)

Проект на сервере — git-репозиторий; каждый пишущий инструмент — коммит под именем агента
с сообщением «что и зачем». Папок предложений и веток нет; конструктор смотрит историю и
откатывает (`revert`). Согласование как сущность (лента с кнопками) — M2 вместе с workbench.
Целевая аудитория — обычные конструкторы, которые могут не знать git: проекты живут на сервере,
синхронизация с внешним origin — необязательная.

## D13. Сборки в изолированном воркере с лимитами — принято (2026-10-19)

Код проекта исполняется только в контейнере-воркере (без сети, лимиты CPU/памяти/процессов),
каждая задача — подпроцесс с таймаутом и audit-hook (запись только в `out/`, без процессов и
сети). Контейнер на задачу с усиленной изоляцией — M2 (публичная площадка).

## D14–D17. Рабочее место (M2) — предложено (2026-10-19), на обсуждении

- **D14. Фронтенд.** Отдельное приложение `web/` (Vite + TypeScript + React, three.js для 3D),
  собранная статика отдаётся сервером по `/`, браузер ходит в `/api` поверх тех же `tools.py`.
  Альтернатива — HTML с сервера + htmx. Рекомендация: React.
- **D15. Вход.** Keycloak realm `home` через oauth2-proxy (как drawio.br); сервер берёт
  пользователя из заголовков прокси в режиме `SKELCAD_AUTH=proxy`; коммиты из workbench — от имени
  пользователя; `/mcp` остаётся на токенах; `/out` уходит за вход. Одна команда, группа `admins`.
- **D16. Задача агенту из workbench.** Сервер сам запускает headless Claude Code в контейнере
  `agent` (сеть: сервер + API Anthropic), ход задачи виден в ленте, на время задачи проект
  «у агента» (D6). Учётные данные — одна сервисная запись; на пользователя — после пилота.
- **D17. Черновик параметров.** Правка в форме собирается во временном снимке и показывается
  как разница с HEAD; коммит — только по «Сохранить».

Принципы интерфейса: ISO 9241-110 (пригодность задаче, самоописательность, управляемость,
устойчивость к ошибкам) и эвристики Нильсена как чеклист ревью каждого шага. Подробно:
`05-m2-plan.md`.

## D6–D10 — отложено, материал для размышления

- **D6. Совместная работа.** Строгая очерёдность на уровне набора изменений (ветка агента в git,
  конструктор принимает merge) против одновременной правки. Обзор: ни одного подтверждения
  в пользу одновременной правки с агентом, Onshape сам рекомендует ветки. Склоняюсь к очерёдности.
- **D7. Адаптер SolidWorks.** Python/COM с early binding сейчас; .NET-добавление после
  стабилизации протокола рецепта. Если ядро примет D1(б), адаптер на C# — обычный плагин-процесс.
- **D8. Дистрибуция — принято вместе с D2.** Self-hosted образ (`docker compose`) первым;
  публичная площадка как экземпляр; у инженера только подписанный мост к САПР; настольная
  сборка Tauri + sidecar + MSIX/winget — позже по спросу.
- **D9. Режим выдачи.** Для SolidWorks/КОМПАС основной — Б (STEP не несёт дерева); режим А
  (готовый комплект) — для малых КБ и стран без лицензий САПР; состав комплекта А определить
  после пилота M2.
- **D10. Пакет стандарта.** Двухслойный: открытый каркас (схема, правила-плагины, шаблоны,
  i18n) + слой данных (таблицы) с указанием источника или поставляемый пользователем.
  Прототипы формата: `package.xml` FreeCAD, реестр `standards[]` BOLTS, правила в духе IDS /
  `.swstd`, SVG-шаблоны TechDraw с autofill. Юридическая проверка до публикации `std-gost`.
