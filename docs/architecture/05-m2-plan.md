# План этапа M2 — рабочее место конструктора в браузере (workbench)

Статус: **редакция 2, в работе (решения D14–D17 приняты 2026-10-19)**. Предыдущий этап — [04-m1-plan.md](04-m1-plan.md)
(закрыт 2026-10-19). Решения этапа D14–D17 — ниже и в [02-decisions.md](02-decisions.md).

## Цель и критерий готовности

Из дорожной карты (раздел 6 документа 01): *self-hosted образ: пользователи, проекты, очередь
сборок, песочница; workbench в браузере: 3D, лента предложений, согласование, сравнение;
удалённый MCP для агентов.* Серверная часть, очередь и удалённый MCP сделаны в M1. Остаётся
рабочее место и пользователи.

Критерий: **конструктор без терминала и без знания git проходит ключевой сценарий (раздел 2
документа 01) на сервере команды**: входит под своей учётной записью, открывает проект, смотрит
3D и замечания, ставит задачу агенту, смотрит, что агент сделал, откатывает лишнее, сравнивает
варианты, забирает комплект. Агент из Claude Code по-прежнему подключён по сети (M1).

Кто пользователь: инженер-конструктор, работает в своей САПР, не программист. Всё, что он знает
про git, должно быть выражено словами «история», «откатить», «кто и когда». Всё, что он знает
про агента: «поставил задачу → получил изменения с объяснением → решил, оставить или откатить».

## Принципы интерфейса

Проектируем по **ISO 9241-110** (принципы диалога) и проверяем каждое изменение по **десяти
эвристикам Нильсена**. Ведущие принципы ISO для этого продукта — четыре; остальные три из
редакции 2020 года (соответствие ожиданиям, обучаемость, вовлечённость) применяем там, где они
не спорят с ведущими.

| Принцип ISO 9241-110 | Что это значит для workbench | Где проявляется |
|---|---|---|
| **Пригодность задаче** | Экран показывает ровно то, что нужно для решения «оставить или откатить» и «какой вариант выбрать»: строка чисел (масса, K_min, error/warning), 3D-разница, замечания. Ничего про git, контейнеры, очереди. | лента коммитов, карточка коммита, сравнение |
| **Самоописательность** | Каждое состояние объясняет себя: у кого модель (у конструктора / у агента), что сейчас происходит (сборка 12 с из 180), почему замечание (код правила, источник, что сделать). Пустые экраны говорят, какой следующий шаг. | шапка, карточки, замечания, пустые состояния |
| **Управляемость** | Любое действие можно прервать (остановить агента, сборку) и отменить (откат коммита — тоже коммит, значит, откат отката возможен). Черновик параметров живёт до явного «Сохранить». Темп задаёт конструктор, а не агент. | откат, черновик, остановка задачи |
| **Устойчивость к ошибкам** | Нельзя сохранить параметр вне диапазона; нельзя выдать комплект при замечании уровня error; нельзя править модель, пока ею занят агент (D6, очерёдность); откат показывает, что именно вернётся, до подтверждения. Ошибка сборки показывает хвост лога и предлагает откат последнего коммита. | формы, шлюз выдачи, блокировка на время задачи, диалог отката |

**Эвристики Нильсена как чеклист ревью.** Каждый шаг плана, меняющий интерфейс, закрывается
коротким файлом `docs/ui/reviews/<шаг>.md`: десять строк, по одной на эвристику, «ок» или
«проблема → что сделано». Шаг не считается сделанным без этого файла. Сам чеклист с
конкретикой для SkelCAD — `docs/ui/checklist.md` (создаётся шагом 0, текст — в приложении
ниже). Это же правило записано в `AGENTS.md`, раздел 2, чтобы агенты, разрабатывающие
workbench, применяли его сами.

Два риска из раздела 7 документа 01 переводятся в правила интерфейса:

- *Проверка предложения дольше ручной работы (METR −19 %)*: карточка коммита отвечает за
  одну минуту — намерение одной фразой (сообщение коммита), строка чисел с дельтами, 3D-разница
  в идиоме Onshape (синий — было, красный — стало), список затронутых сущностей.
- *Over-trust, «приму, посмотрю потом»*: отдельного «принять» нет (D12: оставить = принять),
  но есть явная отметка «Просмотрено», счётчик непросмотренных коммитов в шапке проекта и
  шлюз выдачи комплекта: при error выдача закрыта, пока конструктор не решит.

## Решения этапа (приняты 2026-10-19)

**D14. Фронтенд — отдельное приложение в браузере, статика из сервера.** Папка `web/`:
Vite + TypeScript + React; 3D — three.js через `@react-three/fiber` и `drei` (загрузка GLB с
именованными узлами деталей, подсветка, секущие плоскости three.js, прозрачность, стандартные
виды); эскизы, SVG-виды и будущие чертежи — SVG прямо в React, без canvas-обёрток. Сборка
кладётся в `src/skelcad/server/static/` и отдаётся FastAPI по `/`; API для браузера — `/api`
(тот же модуль `tools.py`, что и MCP). Без SSR и без второго бэкенда. Отвергнуто: htmx (лента,
редактор параметров и 3D-состояние упираются в ручной DOM) и `three-cad-viewer` (свой формат
тесселяции вместо GLB, которого уже достаточно). Решение: так лучше всего ложатся эскизы,
графика и 3D в одном приложении.

**D15. Вход через Keycloak (realm `home`) через oauth2-proxy, как у drawio.br и excalidash.br.**
Браузер → nginx → oauth2-proxy → сервер; сервер узнаёт пользователя из `X-Forwarded-User` и
`X-Forwarded-Email` только в режиме `SKELCAD_AUTH=proxy` и только с адреса прокси. Коммиты
конструктора из workbench подписываются его именем и почтой. `/mcp` остаётся на Bearer-токенах
клиентов. `/out` уходит за вход вместо списка подсетей (хвост M1). Роли в M2: все пользователи
realm — конструкторы одной команды; группа `admins` — управление токенами агентов. Многие
команды и права по проектам — не M2.

**D16. Задача агенту из workbench, любой провайдер LLM.** «Конструктор без терминала»
означает, что агента запускает сервер: поле «Задача агенту» + пометки на модели → контейнер
`agent` ведёт цикл «модель → вызов инструмента → результат» против тех же инструментов MCP
сервера (клиент `mcp` по Streamable HTTP с сервисным токеном), так что набор инструментов у
встроенного агента и у Claude Code один. Провайдер модели не фиксирован: агент говорит с любой
точкой, совместимой с OpenAI Chat Completions (OpenRouter, LiteLLM, Ollama, vLLM, OpenAI,
Anthropic через шлюз) — настройки `SKELCAD_LLM_BASE_URL`, `SKELCAD_LLM_API_KEY`,
`SKELCAD_LLM_MODEL`; второй исполнитель — headless Claude Code (`SKELCAD_AGENT_RUNNER=claude-code`)
для тех, у кого есть подписка. Ход задачи (вызовы инструментов, ответы) виден в ленте живьём,
задачу можно остановить; на время задачи проект «у агента» (D6): правки из workbench закрыты,
кроме «Остановить». Модель и лимит шагов выбираются в настройках сервера, не в задаче.
Claude Code из своего терминала продолжает работать как в M1, коммиты различаются автором.

**D17. Черновик параметров без коммита.** Правка параметров в форме собирается во временном
снимке проекта (как `snapshot` для diff), результат показывается как разница с HEAD; коммит
от имени конструктора делается только по «Сохранить». Так конструктор не плодит коммитов
«попробовал» и не теряет управляемость (ISO) при мгновенном перестроении.

## Устройство

```
 Браузер ──https──► nginx (skelcad.br)
                      /            ──► oauth2-proxy (Keycloak realm home) ──► server: / (статика web/), /api, /out
                      /mcp         ──► server: Bearer-токен клиента (как в M1)
                                            │
                           ┌────────────────┼──────────────────┐
                       worker            /data               agent (контейнер)
                  сборки с лимитами   projects/ out/ jobs/   цикл с LLM (OpenAI-совместимый API
                  (M1)                snapshots/ tasks/      любого провайдера) + MCP-клиент к server
```

- **server** получает: `/api` для браузера (проекты, варианты, отчёт, история, diff по
  коммиту, откат, отметка «просмотрено», черновик, замечания агенту, задачи агенту,
  SSE-поток хода задачи), статику workbench на `/`, режим `SKELCAD_AUTH=proxy|tokens|none`.
- **agent** — тот же образ; команда `skelcad agent --queue /data/tasks`; берёт задачу, ведёт цикл
  с моделью по OpenAI-совместимому API (или запускает headless Claude Code, если так настроено),
  инструменты — через `/mcp` сервера с сервисным токеном; пишет поток событий в
  `tasks/<id>/events.jsonl`, сервер отдаёт его браузеру.
- **Артефакты для 3D-разницы**: GLB для произвольного коммита строится в снимке
  (`snapshots/<project>/<hash>/`) и кэшируется в `out/<project>/_commits/<hash>/`.

### Экраны

| Экран | Содержимое | Принципы, которые он обслуживает |
|---|---|---|
| **Проекты** | карточки: название, варианты, последний коммит (кто, когда, что), состояние «у конструктора / у агента», K_min, error/warning; «Новый проект» из шаблона | самоописательность, пригодность |
| **Вариант** | три области: дерево изделия (узлы, детали, швы, крепёж) · 3D (подсветка по дереву и по замечанию, прозрачность, секущая плоскость, стандартные виды «главный / слева / сверху / изометрия», подогнать) · панель: строка чисел, K по позициям, замечания по уровням (info свёрнуты), допущения | пригодность, распознавание вместо припоминания |
| **Лента** | коммиты сверху вниз, карточка: автор (агент / человек), время, сообщение, строка дельт (масса, K_min, error/warning, затронутые детали), «Показать разницу» (3D-наложение синий/красный + таблица сущностей), «Откатить» (с предпросмотром), «Просмотрено»; счётчик непросмотренных; ход текущей задачи агента | управляемость, статус системы, over-trust |
| **Сравнение** | таблица метрик по вариантам (лучший выделен), 3D бок о бок, переход к варианту | пригодность |
| **Параметры** | форма из `variants/<v>.yaml`: числа с единицами и диапазонами, выбор из каталога (крепёж, прокат, материалы), «Собрать черновик» → дельты → «Сохранить» с сообщением | устойчивость к ошибкам, черновик (D17) |
| **Задача агенту** | текст задачи, пометки на 3D («здесь мало места под ключ» → деталь + точка + текст), «Запустить», «Остановить»; результат — отчёт агента и его коммиты в ленте | управляемость, очерёдность (D6) |
| **Выдача** | комплект (STEP, glTF, SVG, отчёт) по варианту; закрыт при error с объяснением, какие | устойчивость к ошибкам |
| **Подключение агента** (для `admins`) | токены клиентов MCP: создать, отозвать, готовая команда `claude mcp add …` | самоописательность |

Глубокие ссылки: `/p/<project>/<variant>?commit=<hash>&part=<id>` — чтобы замечание в чате
или отчёте агента открывало нужное место.

## Что не входит в M2

Настольная оболочка Tauri; публичная площадка и gVisor; несколько команд и права по проектам;
интерфейс на английском (строки собраны в одном файле, перевод — следующий этап); чертежи и
расчёты (M4–M5); мост к САПР (M3); оптимистичные ветки предложений (D6, M3+); учётные записи
агента на пользователя; выбор модели в самой задаче (модель задаётся в настройках сервера).

## Сценарий приёмки

Проект `bracket`, пользователь — конструктор из Keycloak, терминала и git у него нет.

1. Открывает `https://skelcad.br`, входит через auth.br, видит проекты, открывает `bracket`.
2. На экране варианта `A_fork` находит замечания, кликает по замечанию про шов — шов
   подсвечен в 3D; включает секущую плоскость и смотрит узел; читает K по позициям.
3. Ставит пометку на модели («мало места под ключ у анкера») и задачу агенту: «Сними warning
   по доступу к швам без роста массы более 5 %». Видит ход задачи, ждёт результата.
4. В ленте видит коммиты агента: по строке дельт и 3D-разнице решает за минуту; один коммит
   откатывает с предпросмотром; отмечает остальные «Просмотрено».
5. В параметрах меняет толщину плиты, собирает черновик, видит дельты, сохраняет с сообщением.
6. На сравнении выбирает вариант; на выдаче забирает STEP и отчёт. При error выдача закрыта с
   объяснением.
7. Параллельно агент из Claude Code (терминал автора) делает коммит в тот же проект — он
   появляется в ленте с другим автором.

Как проверяю сам: сценарий прогоняется headless Claude Code с браузером (Playwright MCP)
против живого сервера, скриншоты и протокол — `docs/research/acceptance/m2-*.md`; плюс
ревью каждого экрана по чеклисту в `docs/ui/reviews/`. Приёмка не засчитывается, если
какой-то шаг сценария требует терминала или знания git.

Измеримые пороги: решение по карточке коммита — все нужные данные видны без прокрутки на
экране 1366×768; первая отрисовка варианта `A_fork` ≤ 3 с на LAN; все действия доступны с
клавиатуры; контраст текста по WCAG AA.

## Приложение. Чеклист ревью (текст для `docs/ui/checklist.md`)

| # | Эвристика Нильсена | Что проверяем в SkelCAD |
|---|---|---|
| 1 | Видимость состояния системы | видно, у кого модель; идёт ли сборка или задача и сколько осталось до лимита; непросмотренные коммиты; синхронизация с origin |
| 2 | Соответствие реальному миру | термины конструктора (масса, запас K, шов, анкер, плита), единицы везде (мм, кН, кг, кН·м), виды названы по ЕСКД, цвета разницы как в Onshape |
| 3 | Свобода и контроль пользователя | откат и откат отката; черновик до «Сохранить»; остановка задачи и сборки; закрыть диалог без последствий |
| 4 | Единообразие и стандарты | одна строка чисел на всех экранах; одни имена действий в UI, MCP и CLI; одна цветовая кодировка уровней замечаний |
| 5 | Предотвращение ошибок | диапазоны и единицы в формах; выдача закрыта при error; правки закрыты, пока проект у агента; предпросмотр отката |
| 6 | Распознавание вместо припоминания | дерево и подсветка; замечание ведёт к элементу; выбор из каталога вместо ввода кода; ссылки на коммит и деталь |
| 7 | Гибкость и эффективность | клавиатура и горячие клавиши; глубокие ссылки; те же действия доступны агенту через MCP и из CLI |
| 8 | Эстетика и минимализм | три области, строка чисел, info-замечания свёрнуты, нет служебных терминов (hash показывается коротко и по запросу) |
| 9 | Распознавание и исправление ошибок | ошибка сборки: хвост лога, файл и строка, кнопка «Откатить последний коммит»; конфликт с origin: что сделать |
| 10 | Помощь и документация | у каждого замечания «почему» (код, источник, что сделать); пустые состояния подсказывают шаг; руководство конструктора |

Формат `docs/ui/reviews/<шаг>.md`: заголовок, дата, экран; десять строк «N. ок» или
«N. проблема → что сделано»; при необходимости скриншот в той же папке.
