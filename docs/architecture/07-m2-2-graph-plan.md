Статус: **в работе с 2026-10-20** (решения D22–D27 приняты 2026-10-20; статусы шагов в таблице). Предыдущий этап —
[06-m2-1-sketches-plan.md](06-m2-1-sketches-plan.md) (закрыт 2026-10-19). Этап открывает дорожную карту
масштабирования после обсуждения 2026-10-20 (см. [дорожную карту](#дорожная-карта-после-m21) внизу и
исследование `docs/research/research_notes/Мировая практика — компоновка, PMI, дерево узлов, база связей.md`).

Запрос конструктора: «решение у нас серверное, и в рамках сложных изделий потребуется хранить большое
количество сущностей и разнообразные связи — получатся графы связей»; «я бы использовал сразу PG для связей».

## Цель и критерий готовности

Сегодня модель, варианты, замечания и согласование живут в git-репозитории проекта, а запрос по модели
(`model_query`) работает по одному проекту и по пути внутри YAML. Вопросы «где используется», «что зависит
от этой базы», «какие узлы крепятся к интерфейсу», «где во всех проектах анкеры M16» требуют обхода связей,
а дерево компоновок (M3) без этого не собрать: ребёнку нужна окрестность, а не весь YAML родителя.

Критерий: **(а) сервер держит в Postgres производный индекс сущностей и связей всех проектов, пересобираемый
по коммитам и сборкам; удалить базу и поднять заново можно без потерь; (б) конструктор ищет по всем проектам
(«M16», «стена», «u_bracket») и у выбранной сущности видит её связи с переходом к ним; (в) агент одним
вызовом получает окрестность сущности на 1–2 шага по выбранным типам связей, «где используется» и поиск,
не читая YAML целиком; (г) после правки файла или сборки индекс обновлён до возврата ответа.**

## Принципы

- **Система записи не меняется.** Истина — git с YAML (D1, D12); индекс одноразовый, в нём нет ничего, чего
  нет в репозитории и в комплекте сборки. Согласование, замечания и история остаются в git.
- **Словарь связей задан явно** (`skelcad.graph.extract.RELATIONS`): содержит, привязан к базе, крепится к
  интерфейсу, нагрузка через, соединяет, крепит, материал, из каталога, пакет стандартов, размер к,
  замечание к, замечание конструктора к, расчёт по. Новые типы — через словарь, не строками по месту.
- **Глобальная адресация** сущности: проект, вариант (пусто — уровень проекта), ссылка в грамматике
  `kind:id[/kind:id]`, той же, что у замечаний, размеров и `data-ref` эскизов (`part:p/hole:h`,
  `interface:wall`). Каталожные позиции и материалы — сущности (`item:anchor/M16`, `material:09Г2С`), чтобы
  «где используется» работало через проекты.
- **Запросы — SQL с рекурсией**, граф в памяти не нужен; Apache AGE или выгрузка в Neo4j — позже и только для
  анализа, без смены системы записи (D27).
- **Postgres сразу** (по решению конструктора): в compose — сервис `db`, локально и в тестах — встроенный
  сервер через `pgserver` (`SKELCAD_DATABASE_URL=embedded`), та же схема и те же запросы.

## Схема индекса

- `graph_entity (project, variant, ref, kind, eid, name, text, data jsonb, commit, updated_at)` — ключ
  (project, variant, ref); `text` — строка для поиска (id, имя, примечание, роль, теги).
- `graph_relation (project, variant, src, dst, kind, data jsonb, commit)` — ключ (project, variant, src, dst,
  kind); индексы по `src`, `dst` и по `dst` без проекта (поиск использования через проекты).
- `graph_state (project, variant, commit, entities, relations, indexed_at)` — что и когда проиндексировано;
  повторный проход пропускает неизменившийся коммит и сборку.
- `graph_meta (key, value)` — версия схемы; при смене версии таблицы пересоздаются (индекс одноразовый).

Уровень проекта (`variant = ''`): `project:<name>`, `variant:<v>`, `standard:<s>`, `load:<name>`,
`constraint:<name>`, `datum:<id>`, `interface:<id>`, `envelope:<id>`, `surrounding:<id>`, `assumption:<id>`,
`review:<id>`. Уровень варианта (из последней сборки): `unit:<id>`, `part:<id>`, `part:<id>/hole:<h>`,
`weld:<id>`, `fastener:<id>`, `material:<name>`, `item:<type>/<size>`, `dim:<id>`, `finding:<n>`, `calc:<id>`,
`metric:<id>`. Связи уровня варианта могут вести к сущностям уровня проекта (`unit → interface`).

## Итог M2.2

Сделано 2026-10-20 (коммит этапа — см. журнал git):

- `skelcad.graph`: словарь видов сущностей и типов связей, извлечение из `project.yaml` (проект, пакеты
  стандартов, нагрузки, ограничения, базы, интерфейсы, зоны, обстановка, допущения, варианты, замечания
  конструктора) и из комплекта сборки (узлы, детали, отверстия, швы, крепёж, материалы, позиции каталога,
  замечания, расчёты, метрики, размеры); индексатор по коммитам (слушатели `Workspace`), по сборкам и при старте
  (неизменившееся пропускается по `graph_state`); запросы: окрестность рекурсивным SQL (`hops`, `kinds`,
  `direction`), «где используется» через проекты, поиск, сводка.
- Сервер: `SKELCAD_DATABASE_URL` (URL Postgres или `embedded` → `pgserver`), `/health` → `graph: ok | off | error`,
  `/api/graph/search`, `/api/graph/stats`, `POST /api/graph/reindex`, `/api/projects/<p>/graph/links`,
  `/api/projects/<p>/graph/where-used`; без базы — 503 словами. Инструменты агента `links`, `where_used`,
  `search`; памятка обновлена. Compose: сервис `db` (postgres:16), пароль создаёт деплой, smoke-check
  проверяет `graph: ok`.
- Рабочее место: поиск по всем проектам на экране «Проекты» (`?q=`), блок «Связи» на экране «Вариант» у
  выделенной детали, размера, ссылки замечания или сущности компоновки, переход по связи, «Где используется»;
  адреса `?ref=` для сущностей компоновки. Ревью `docs/ui/reviews/14-graph.md`.
- Приёмка 7/7: `docs/research/acceptance/m2-2-graph.md`. Тесты: 7 новых в `tests/test_graph.py` (встроенный
  Postgres), 3 vitest.
- Попутно: `Interface.params` принимает списки (положения отверстий, как пишет генератор планки) — старый
  комплект `plate_m10` снова читается; индексатор переживает нечитаемый комплект варианта.

Хвосты: группировка результатов поиска по проектам и фильтр по виду; окрестность на 2 шага в интерфейсе;
сущности коммитов и ленты в графе (кто что менял — пока только git); операционные данные (задачи, лента) в ту
же базу при втором экземпляре сервера; выгрузка таблицы связей в Neo4j / Apache AGE для анализа.
