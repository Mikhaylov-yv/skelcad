# План этапа M1 — агентный контур (сервер с точкой MCP)

Статус: **план, 2026-10-19**, редакция 2 после обсуждения. Предыдущий этап —
[03-m0-plan.md](03-m0-plan.md) (закрыт 2026-10-16).

## Цель и критерий готовности

Из дорожной карты (раздел 6 документа 01): *MCP-сервер с инструментами из 4.4; песочница
генераторов; предложения.* Критерий: агент из Claude Code ведёт пилот от задачи до комплекта без
ручного запуска скриптов.

Критерий раскрыт в сценарий приёмки (ниже): конструктор ставит задачу текстом; агент через
точку MCP на сервере читает модель, измеряет, правит файлы проекта, строит, проверяет; каждое
его изменение — коммит в git с подписью агента; конструктор смотрит историю и либо оставляет,
либо откатывает; в `out/` лежит комплект (STEP, glTF, SVG, `report.json`, `model.yaml`,
`compare.html`).

## Решения (приняты в обсуждении 2026-10-19)

**D1. Языки плагинов — закрыто.** Генераторы и плагины — только Python, исполняются на сервере.
Протокол для плагинов на других языках не описываем, пока не появился первый такой плагин.
Поле `Text` уже принимает `{ru:…, en:…}`; сообщения правил остаются русскими до workbench (M2).

**D11. Сервер с встроенной точкой MCP, не локальный процесс.** SkelCAD — сервер (FastAPI),
у которого MCP — одна из точек: `https://<host>/mcp` (Streamable HTTP). Claude Code и любой
другой клиент подключаются по сети с токеном, как к `drawio.br` и `excalidash.br`. Локальный
запуск по stdio не делаем. Это переносит часть «server» из M2 в M1, но ровно ту, что нужна
для точки MCP: приложение, токены, образ, `docker compose`. Пользователи, роли, очередь сборок
на много команд и OIDC — по-прежнему M2.

**D12. Изменения агента — обычные коммиты в git.** Ни папок предложений, ни веток. Проект на
сервере — git-репозиторий; каждый инструмент, который что-то меняет, делает коммит с автором
«агент» и именем клиента (по токену) и сообщением, которое агент пишет сам. Конструктор видит
в истории, кто что сделал, откатывает (`git revert`) или переделывает. Это даёт агенту простор
для долгой автономной работы: он может делать десятки итераций «поправил → собрал → измерил»,
а конструктор смотрит результат по истории и сводкам. Согласование как отдельная сущность
(`proposals`, `decisions`) откладывается до workbench (M2): там оно станет лентой коммитов
с кнопками.

**D13. Сборки — в изолированном воркере с лимитами.** Код проекта (генератор, плагины)
исполняется не в сервере, а в отдельном контейнере-воркере с ограничениями по CPU, памяти,
числу процессов, без сети, и с таймаутом на задачу. Каждая задача — отдельный подпроцесс
внутри воркера; зависший или упавший генератор не трогает сервер и сессию агента. Контейнер
на каждую задачу с усиленной изоляцией (gVisor и т. п.) — M2, для публичной площадки.

## Устройство

```
                   ┌───────────────────────── docker compose ───────────────────────────┐
 Claude Code ──MCP/HTTP──► server (FastAPI)                     worker (контейнер с лимитами)
   токен                     /mcp   инструменты                    ждёт задачи в /data/jobs
                             /api   то же для CLI и workbench      задача = подпроцесс с таймаутом
                             /out   артефакты сборок (статика)     генератор + OCCT + правила
                                │                                        │
                                └────── общий том /data ─────────────────┘
                                        projects/<name>/   git-репозитории проектов
                                        jobs/<id>/         request.json -> result.json
                                        out/<project>/     артефакты
                                                 ▲
 Конструктор ──git push/pull──── git.br ◄───────┘ (origin проекта; сервер pull перед задачей, push после коммита)
```

- **server** — FastAPI; MCP смонтирован через `mcp` 1.x (`mcp>=1.30,<2`; в 2.x другой API
  сервера, переход отдельным шагом). Инструменты реализованы в модуле без зависимости от SDK,
  тот же модуль обслуживает `/api` и CLI.
- **worker** — тот же образ, команда `skelcad worker`. Очередь — файловая (`/data/jobs`), без
  Redis: сервер кладёт `request.json`, воркер отвечает `result.json`, сервер ждёт с таймаутом.
  Лимиты контейнера в compose: `cpus`, `mem_limit`, `pids_limit`, `network_mode: none`.
  Внутри — подпроцесс на задачу с `RLIMIT_CPU`/`RLIMIT_AS` и `SIGKILL` по таймауту.
- **projects** — git-репозитории в `/data/projects/<name>`. Если у проекта есть `origin`
  (git.br), сервер делает `pull --ff-only` перед каждой задачей и `push` после каждого коммита;
  при конфликте — ошибка инструменту с просьбой разрешить руками.
- **Авторство.** Токен клиента (`SKELCAD_TOKENS="claude-code:…;cursor:…"`) → автор коммита
  `SkelCAD agent (claude-code) <agent@skelcad>`. Конструктор коммитит обычным git под своим
  именем. Так история отвечает на вопрос «кто что сделал».
- **Развёртывание** — по стандарту домашних сервисов (`home-cicd`): образ, compose, nginx
  на `cloud`, домен `skelcad.br`, `claude mcp add --transport http skelcad https://skelcad.br/mcp
  --header "Authorization: Bearer …"`.

## Инструменты MCP

Все инструменты принимают `project` — имя проекта на сервере. Ответ — короткая текстовая
сводка первой строкой и JSON; полная модель только по явному срезу.

| Инструмент | Вход | Выход | Назначение |
|---|---|---|---|
| `project_list` | — | проекты на сервере, origin, последний коммит | что есть |
| `project_create` | `name`, `template?` (bracket, pipe_support, empty), `origin?` | проект-репозиторий | начать новое изделие |
| `project_read` | `project`, `section?` | спецификация, варианты, параметры, допущения | первый взгляд |
| `model_query` | `project`, `variant`, `path?` (`parts`, `parts[id=cheek_L]`, `welds`, `skeleton`) | срез разрешённой модели | читать кусками |
| `files_read` | `project`, `path` | содержимое файла проекта | исходники генератора, YAML |
| `files_write` | `project`, `files: {path: content}`, `message` | коммит (hash, автор) | изменить проект; один вызов = один коммит; пути только внутри проекта, без `out/` и `.git` |
| `history` | `project`, `limit?`, `path?` | коммиты: автор, время, сообщение, файлы | кто что сделал |
| `revert` | `project`, `commit`, `message?` | коммит-откат | агент отменяет свой неудачный шаг |
| `diff` | `project`, `variant`, `a` (commit/HEAD~1), `b` (commit/HEAD) | изменённые сущности по id, дельты объёма и положения деталей, дельты сводки | что изменилось между двумя состояниями |
| `context_tables` | `project` | таблицы контекста и ключи | что есть в пакетах стандартов |
| `context_lookup` | `project`, `table`, `key` | запись | каталожная позиция |
| `context_search` | `project`, `query`, `table?` | совпадения | найти типоразмер, материал |
| `standards_list` | — | установленные пакеты | диагностика |
| `build` | `project`, `variant?`, `export?` | сводка, замечания warning+, ссылки на файлы в `/out` | модель → геометрия → проверки → комплект (через воркер) |
| `check` | `project`, `variant?`, `scope?` (rules/geometry/calc/all), `all?` | замечания, K по позициям | быстрая проверка; `scope=geometry` — бывший `validate` |
| `compare` | `project`, `variants?` | таблица метрик, лучший по каждой, ссылка на `compare.html` | сравнение |
| `measure` | `project`, `variant`, `op`, `args` | число/вектор с единицами | `mass`, `cog`, `bbox`, `distance(a,b)`, `clearance(a,b)`, `interference(a,b)`, `section(plane)`, `part(id)` |
| `render` | `project`, `variant`, `view` (main/left/top/iso), `highlight?` | PNG + ссылка на SVG | «посмотреть глазами» |
| `review_list` / `review_resolve` | `project` / `project`, `id`, `answer` | замечания конструктора | обратная связь; шаг 8, если нужна до workbench |

Семнадцать основных инструментов и два необязательных. Ресурсы и промпты MCP не используем.

## Автономная работа агента

Цикл, который описывает `AGENTS.md` и которому агент следует сам:

1. `project_read`, `check` — понять задачу и текущее состояние.
2. `measure`, `context_search`, `render` — заземлиться в числах и каталогах.
3. `files_write` с осмысленным сообщением — одно логическое изменение на коммит.
4. `build` или `check` → `diff(HEAD~1, HEAD)` — убедиться, что изменение дало ожидаемое.
5. Повторять 2–4 столько, сколько нужно; тупиковую ветку — `revert`.
6. Итог — `compare` и сообщение конструктору: что сделано, какие коммиты, какие допущения.

Конструктор ограничивает автономию не инструментами, а задачей и временем; у сервера есть
лимит на задачу воркера, а не на число шагов агента.

## Песочница (воркер)

| Ограничение | Где | Значение по умолчанию |
|---|---|---|
| CPU, память, число процессов, сеть | контейнер `worker` в compose | `cpus: 2`, `mem_limit: 4g`, `pids_limit: 256`, `network_mode: none` |
| Время задачи | сервер (ожидание результата) и воркер (`SIGKILL` подпроцесса) | 120 с на вариант, настраивается в `project.yaml` → `limits` |
| CPU и адресное пространство подпроцесса | `resource.setrlimit` в воркере | 110 с, 4 ГБ |
| Файлы | подпроцесс видит `/data/projects/<name>` только для чтения и `/data/out/<name>` для записи | — |
| Окружение | `python -I`, `cwd` — папка проекта | — |

Сервер и воркер — один образ, разные команды; воркеров можно поднять несколько.

## Сценарий приёмки

Проект `bracket` на сервере, вариант `A_fork`, известная проблема: K по анкерам 1.14 при
требуемом 1.5 (предупреждение `K-anchor_NV`).

1. Конструктор в Claude Code: «Подними запас по анкерам варианта A до K ≥ 1.5 при минимальном
   росте массы. Работай автономно, в конце покажи, что менял».
2. Агент: `project_read` → `check` → `context_search("M20")` → `measure` → `files_write`
   (variants/A_fork.yaml, коммит «анкеры M20») → `build` → `diff(HEAD~1, HEAD)` → ещё
   итерации при необходимости, тупики через `revert` → `compare` → отчёт конструктору.
3. Конструктор: `git log` в своём клоне (или `history`), смотрит `compare.html` по ссылке
   `/out`, откатывает лишнее `git revert`, если нужно.
4. Проверка: комплект в `/out/bracket/A_fork/`, история коммитов с автором-агентом, ни одного
   ручного запуска скриптов. Повтор на `pipe_support`.

## Сознательно не делаем в M1

- Пользователи, роли, OIDC (Keycloak), многокомандная очередь — M2; в M1 статические токены.
- Workbench в браузере, лента коммитов с кнопками принять/откатить, 3D-diff — M2.
- Папки или ветки предложений, журнал решений как сущность — не нужны при модели «всё в коммитах».
- Контейнер на каждую задачу и gVisor — M2, публичная площадка.
- Плагины не на Python — пока не появится первый.
- i18n сообщений правил — M2.
- Локальный MCP по stdio — не делаем.

## Риски этапа

| Риск | Смягчение |
|---|---|
| Смена API `mcp` SDK (2.x) | закрепить `<2`; регистрация в одном модуле, реализации не зависят от SDK |
| Шумная история из мелких коммитов агента | один вызов `files_write` — несколько файлов и одно сообщение; `AGENTS.md`: одно логическое изменение на коммит |
| Конфликты между клоном конструктора и сервером | pull `--ff-only` перед задачей, push после коммита, конфликт — ошибка инструменту, не тихое слияние |
| Большие ответы забивают контекст агента | срезы `model_query`, сводка первой строкой |
| Нет колёс `resvg-py` под платформу образа | запасной путь: SVG текстом + ссылка; `cairosvg` второй вариант |
| Файловая очередь задач при нескольких воркерах | атомарное переименование `request.json` → `claimed/`; при росте — Redis, не раньше M2 |
| Докер-сокет серверу не нужен | воркер — постоянный контейнер с лимитами, задачи через том; сервер не управляет контейнерами |
